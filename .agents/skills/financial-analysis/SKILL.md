# 企业授信财务分析 Skill（financial-analysis）

## 1. 目标、适用范围与边界

本 Skill 服务于 **「企业授信研究Agent」**，将可核实的企业财务资料转化为**可复算、有证据、符合银行授信调查习惯**的财务分析结果。

- **分析目标**：说明企业财务状况发生了什么变化、可能为什么变化、该解释是否合理、对银行授信关注点有何影响，以及还需核实什么。
- **首测企业**：石家庄以岭药业股份有限公司（002603.SZ）。此处只是测试对象；不得在 Skill 中预填或臆造真实财务数值、交易对手或银行信息。
- **第一版输入**：用户仅输入公司名称/股票代码；系统自动检索可公开访问的上市公司年报、财务附注、审计报告及公告；默认重点对比 **2024、2025 年年度数据**，必要时引用 2023 年期初数进行平均余额分析。报告期间可配置。
- **默认主体与口径**：上市公司**合并报表**，原始披露的会计准则、币种和单位必须记录。不能将母公司、子公司或其他主体的数字混入合并口径。
- **后续扩展**：取得合法授权且满足数据安全要求时，可以分析客户经理提供的财务明细、银行账户资料和流水。**第一版没有上传入口，也不能假装掌握非公开流水。**
- **不做的事**：自动授信审批、核定授信额度或利率、将推测写成事实、直接据单一比率判定企业违约、绕开数据源访问限制、处理未经授权的客户保密数据。
- **核心原则**：数据准确优先于报告完整；结论可靠优先于篇幅。缺失科目可输出“未取得/尚无法判断”。

> `SKILL.md` 是供主 Agent 使用的专业分析规范，**本身不负责计算或联网**。PDF/表格提取、数值计算、证据登记、关键事实校验和 Markdown 文件组装由经过测试的 Python Tools 完成；正式财务分析正文必须由运行时实际调用的 DeepSeek 基于这些材料撰写。Codex 能发现项目级 Skill，不代表独立部署的 Agent 会自动加载；运行时应显式注册、选择和加载。

## 2. 触发条件、输入与配置

### 2.1 触发条件

适用于：授信报告的“财务分析”章节、财务报表分析、重点科目变化原因、应收应付与营运资金、短期借款、资产负债情况、收入现金流匹配、财务异常和待补充尽调材料。

### 2.2 输入契约

必需：`company_identity`（公司名称、证券代码、交易所）。

建议输入（由公开资料获取工具提供）：

- `periods`：可比年度，默认 `[2024, 2025]`；可扩展至 2023–2025 年；
- `statements`：资产负债表、利润表、现金流量表的原始数据及标准化字段；
- `notes`：财务报表附注、管理层讨论与分析、审计意见及相关公告；
- `sources`：每个数据点/业务事实的来源 ID、文档标题、原始 URL、公告日期、页码/章节；
- `optional_bank_statements`：**仅未来授权上传版本适用**，第一版固定为未提供。

默认参数：

```yaml
material_yoy_change_pct: 20.0  # |同比变化率| >= 20% 触发重点分析；恰好20%也触发
periods: [2024, 2025]
statement_scope: consolidated
source_policy: official_public_disclosures_first
output_language: zh-CN
include_unverified_hypotheses: true  # 必须显式标为“可能原因，待核实”
include_bank_statement_analysis: false  # 第一版禁用，后续仅凭授权资料启用
```

## 3. 银行授信财务分析的写作方法（必须执行）

每个重点科目按以下顺序输出：

1. **金额**：列出上一年度、本年度余额/发生额，明确单位、期间及合并口径。
2. **变化**：列出增减金额、同比变化率（或增长率）、变化方向。
3. **原因**：查找年报/附注/公告已披露的原因；不存在直接证据时仅提出合理假设，不得断言。
4. **合理性**：结合主营业务、收入、上下游结构、账期、周转率、利润、现金流和行业特点做交叉验证；分别说明“支持该解释的证据”“与该解释相矛盾的现象”“仍缺少的证据”。
5. **授信关注点**：说明可能对流动性、债务偿付、回款和资金占用产生的影响，必要时给出待核查材料/问题。
6. **证据**：每条重要金额与已披露原因需要来源定位；**推断与事实严格分开**。

**示例（完全虚构，不得作为以岭药业事实）**：

> 公司2024年末应收账款为1,000万元，2025年末为1,200万元，增加200万元，同比增长20.00%，达到重点分析阈值。若公司同期销售扩大、赊销比例上升或结算账期较长，应收账款增加可能有经营层面的解释，但这些原因**尚未得到资料证实**。需核对营业收入增长幅度、应收账款周转天数、主要欠款客户、账龄和期后回款，以判断资金占用增加是否合理。`[模拟案例，无真实来源]`

> **不能直接写成**：“主要由于公司扩大销售规模，行业普遍押账，因此应收账款增长20%。”除非企业年报或其他可核实资料确实支持相应原因，且已注明来源。

### 3.1 变化幅度与重要性规则

- 当科目 `|同比变化率| >= 20%`，**必须重点分析**：查阅相关附注、形成原因判断并给出风险关注点/核查问题；恰好 **20.00% 算触发**。
- 低于20%也不能完全忽视：**绝对金额重大**、由正转负、扭亏为盈、利润与现金流背离、期末货币资金明显受限、即将到期的短期债务、重要减值或关联交易等，都应优先分析。
- 以 20% 作为**研究触发阈值**，不是银行统一的风险认定标准，更不能等同于“超过20%就是不合理”。
- 基期为0、接近0、缺失或指标发生正负切换时，不输出误导性百分比；标为“新增/消失/由正转负/不可比”，优先检查金额与原因。
- 对金额很小而变化率很高的项目，标注金额的重要性，不夸大风险；对金额重大但增幅小的项目仍分析其占比与资金占用。
- 重大变化分析优先级：`必须核查的异常/数据矛盾 > 关键科目>=20% > 其他重大风险信号 > 普通稳定科目`。

### 3.2 同比变化率的统一算法

对于两期可比金额（同主体、同范围、同币种及单位）：

```text
变化额 = 本期金额 - 上期金额
变化率(%) = (本期金额 - 上期金额) / |上期金额| × 100%
```

- 对上期金额 > 0 的余额或收入类科目，可以称“同比增长/下降”；
- 对上期金额 < 0 的项目，应写“亏损扩大/收窄”等方向性表述，不机械使用“增长”；
- 上期金额为0或无法确认时，变化率为 `null`，并说明不能计算；
- 负值、重分类、追溯调整、停业或合并范围变化时，应单独标注“可比性限制”；
- 资产负债率、毛利率、净利率等**比率本身变化**用“百分点”描述，不将同比增幅与百分点混淆；
- 精度与舍入规则由 Python Tools 统一实现，先用未舍入值计算，再在报告中按约定显示两位小数。

## 4. 必须覆盖的重点财务科目

> 下表是“检查清单”，不意味着公开年报必然披露所有明细。无法获得的资料必须明确“公开资料未披露/尚无法核实”，并进入待补充清单。

| 模块 | 必须分析的内容 | 重点核查逻辑及缺失资料 |
| --- | --- | --- |
| **货币资金** | 两期金额、占总资产比例、受限资金、币种（如披露）、存放银行（如有可靠来源） | 是经营积累、融资流入还是出售资产形成？与短期借款、经营现金流是否匹配？**公开年报通常不能完整列出存款所在银行及账户余额**，不得凭推断填写；需补充开户行、账户余额明细和银行对账单 |
| **应收账款** | 两期金额、收入与应收账款增速对比、余额来源/主要客户、赊销模式、信用账期、账龄/逾期、坏账准备、周转情况 | 是否收入增长导致、客户回款放缓、结算政策变化或大客户集中？核查前五大欠款方、账龄、期后回款和减值政策；账期不可用行业经验代替企业合同约定 |
| **预付款项** | 变动金额与比例、主要预付对象、预付采购或项目背景、账龄与长期未结算情况 | 预付锁定原材料、订单优惠或产能只是**可能解释**；须核对采购合同、履约进度、价格及是否关联方；检查长期挂账 |
| **固定资产** | 余额、主要类别（房屋建筑物、机器设备等）、新增/处置/折旧/减值、在建工程转固 | 是否有真实产能建设、设备更新或并购变化？与资本开支、销售扩张和产能利用情况是否一致；不要把未披露的具体设备名称写成事实 |
| **短期借款** | 两期金额、借款类型、主要贷款银行/机构（披露时）、利率/到期日/担保及质押（披露时） | 资金用途是什么？新增借款是否支撑生产经营或填补现金缺口？与可动用货币资金、经营现金流和短期偿债压力是否匹配；**未披露债权银行不得臆造** |
| **应付账款** | 两期余额、主要来源（原材料/商品/设备采购等）、供应商集中度、账期和逾期情况（如披露） | 是否采购规模扩大或付款账期拉长？与存货、采购成本及经营现金流是否匹配；需防范拖欠供应商导致的流动性压力 |
| **主营业务收入** | 营业收入总额、分产品/业务收入及占比、同比增减、毛利率、主要收入来源 | 核查销量、价格、产品结构、新业务、并表变化及一次性因素；区分营业收入与主营业务收入以及不同披露口径；关注收入与应收、现金流的匹配 |
| **经营活动现金流** | 现金流净额、经营流入流出、收现与利润匹配情况 | 收入利润增加但现金流下降时，优先检查应收、预付款、存货、应付及税费变化；不能用账面现金余额替代经营现金流 |
| **存货（建议重点覆盖）** | 两期余额、原材料/在产品/库存商品构成、跌价准备及周转 | 库存增加是否与生产销售匹配？是否存在积压、减值或生产周期变化；医药企业需关注批次、有效期等经营风险（如有披露） |
| **银行流水核查（第二阶段可选）** | 在获得合法授权的原始流水后，统计主要交易对手、前五大客户回款和采购付款、期间规模和异常往来 | 第一版公开资料不做此项；流水中的入账/出账**不必然等于销售收入/采购成本**，需剔除借款、往来款、内部划转、税费等非经营收付并与账簿核对 |

### 4.1 应收账款的专项分析逻辑

除20%触发规则外，如出现“应收账款增速高于营业收入增速”“应收周转率下降”“坏账准备明显变化”“大额应收账款长期未收回”任一信号，也应列为重点。按顺序核查：

1. **规模变化**：应收余额变化额、变化率，收入变化额、变化率，计算应收账款/营业收入的粗略比例（注明仅为期末余额对全年收入，**不是周转率**）。
2. **客户来源**：已披露前五大欠款单位或客户集中度；未披露时不得臆造名单。
3. **形成机制**：销售赊销、结算方式和合同账期；先找证据，再分析是否符合行业业务模式。
4. **账龄与减值**：应收账款账龄、按组合计提的坏账准备、单项减值、期后回款（如披露）；区分“账龄”和“合同约定到期后的逾期天数”。
5. **现金流匹配**：销售商品、提供劳务收到的现金和营业收入的差异（注意含税、预收及非现金因素）；不得把差异直接等同造假。
6. **授信结论**：将已核实的资金占用变化与仍需核实的客户集中、账期延长、坏账风险分别表述。

### 4.2 货币资金与短债联合核查

- 先列出货币资金总额、受限金额（如披露）、可动用金额（只有具备可靠数据时计算），再列短期借款及一年内到期债务；
- 分析现金是否主要来自融资而非经营，关注短期债务集中到期和现金受限；
- 若没有债务期限和受限资金完整信息，不可直接下“流动性充足”的确定结论；
- “存在哪些银行”“贷款来自哪些银行”属于**应核查的明细**，只在存在明确证据时展示具体机构名称。

## 5. 必须分析的财务比率（可得时）

计算必须由 Python Tool 完成，并保存公式、输入数据及单位：

| 分析方向 | 推荐指标 | 计算或说明 |
| --- | --- | --- |
| 偿债能力 | 资产负债率 | 总负债/总资产；同口径比较 |
| 偿债能力 | 流动比率 | 流动资产/流动负债 |
| 偿债能力 | 速动比率 | （流动资产－存货－预付款项等非速动项目）/流动负债；明确采用的口径 |
| 盈利能力 | 毛利率、净利率 | 毛利润/营业收入；净利润/营业收入（需说明净利润口径） |
| 盈利能力 | 营业收入、营业利润、归母净利润增长率 | 三者分开，不混写利润表科目 |
| 营运能力 | 应收账款周转率与天数 | 营业收入/平均应收账款（或按规范选含票据口径）；必须有两端可比余额，披露分母定义与天数口径 |
| 营运能力 | 存货周转率与天数 | 营业成本/平均存货；必须有两端余额 |
| 现金流 | 经营现金流/净利润 | 观察利润现金含量；分母为0、负值时特别处理 |
| 现金流 | 销售收现指标 | 根据可比收入与销售收现额计算；披露含税及业务口径差异 |

可根据证据进一步分析：有息负债、利息保障倍数、现金短债比、资本开支等。避免在关键数据缺失时强行计算。

## 6. 资料来源、证据分级与原因合理性评价

### 6.1 来源优先级

1. 证券交易所/巨潮资讯的正式年度报告、审计报告、财务附注、公告及更正公告；
2. 公司投资者关系披露、官方经营资料；
3. 政府/监管部门公开数据和行业资料（只能辅助解释行业环境，不可直接替代企业特定数据）；
4. 可追溯的其他公开来源，仅作为线索并标明可靠性限制。

每个原始数据点至少保留 `source_id`、`title`、`url`、`published_at`、`fiscal_period`、`statement_scope`、`original_unit`、`page_or_section`、`extraction_status`。中文 PDF 与 PDF 物理页码差异应予记录或转换，不得生成未验证的页码。

### 6.2 区分三种陈述

| 等级 | 可用措辞 | 要求 |
| --- | --- | --- |
| `verified_fact` 已核实事实 | “2025年末应收账款为……”“年报披露……主要由于……” | 有明确可追溯的年报数据或公司披露及来源 |
| `supported_inference` 有依据的分析判断 | “结合收入增长和结算条款，增加可能与……有关” | 至少能指出支持和反证/不确定性，不冒充公司原文 |
| `unverified_hypothesis` 待核实假设 | “可能与赊销扩大有关，尚需核查销售合同、账龄和期后回款” | 必须显式标注待核实，不能用“主要由于”“表明”作无依据断言 |

### 6.3 判断原因是否合理

对每项重点变化至少问：

1. 公司是否在年报/附注**直接解释**了变化？该解释是否与金额、期间和业务口径一致？
2. 若原因是“业务规模扩大”，收入、主营产品、存货、应收账款和销售现金回款是否支持？
3. 若原因是“集中采购/锁价预付”，预付款、原材料采购、存货和采购承诺是否相符？
4. 若原因是“购置固定资产”，固定资产增加、在建工程转固和投资现金流是否一致？
5. 若原因是“增加短期借款”，借款余额、现金流入、财务费用和用途披露是否互相印证？
6. 是否存在其他解释，如并购并表、会计政策变更、重分类、季节性、减值计提或一次性事项？
7. 是否存在反面证据、信息缺口或存在较大不确定性？如果有，应列出补充核查事项。

结论使用：`合理且有披露支持`、`具有一定合理性但证据不足`、`存在不匹配需重点核查`、`无法判断`。**这些是研究判断，不是统一的授信审批评级。**

## 7. 标准工作流程

1. **主体与报告期确认**：确认公司全称、证券代码、研究基准日、分析年度和合并/母公司口径。
2. **官方资料获取**：优先最新完整年报及可比年度年报，检查更正公告、审计意见和重大会计调整。
3. **科目抽取**：解析三大报表及附注，把数值、原始科目名、单位、币种、页码、来源写入结构化数据。
4. **数据校验**：识别空缺与重复；校验资产=负债+权益、同一期间和合并范围、单位换算、利润表/现金流量表的期间属性；允许公开报告合理舍入差异但要记录。
5. **确定性计算**：调用 Python 工具计算变化额、变化率、指标和必要的交叉校验；禁止 LLM 徒手计算关键数值。
6. **重点科目排序**：执行 `>=20%` 规则及重大金额/正负切换等覆盖规则，形成需深入查附注的科目列表。
7. **原因检索**：从相应财务附注、经营讨论、产品/客户披露中查找具体原因，给证据分级。
8. **合理性验证**：对高优先级变动进行业务和现金流交叉验证，区分有证据事实和待核实假设。
9. **DeepSeek 撰写授信分析文字**：把必要的结构化事实、指标、附注证据、缺失信息和来源交给模型，由模型按“金额→变动金额及比例→原因及证据→合理性→授信风险及待核查问题”生成自然语言分析，并在段落中引用对应 ID。
10. **生成待补充清单**：公开信息缺少的开户行及账户、账龄明细、客户合同账期、前五大销售/采购流水、贷款明细等，归类为后续尽调问题。
11. **逐段复核与机械组装**：Python 验证报告关键数值、期间、来源和事实支持关系；通过的模型段落原样进入 Markdown，失败或缺失的章节明确标记未完成。验证失败不能触发固定模板替写，也不能把“未披露”误写为“没有”。

## 8. 建议的数据模型与输出契约

V2.3 已将本节落实为 `credit_research_agent.financial` 中的 Pydantic 模型和确定性函数。金额在事实层统一保存为人民币元和 `Decimal`，JSON 输出为精确十进制字符串；报告展示格式不得回写或污染原始事实。原因使用 `disclosed_reason / supported_inference / unverified_hypothesis` 三层契约，合理性评价不得把推断升级为披露事实。正式分析正文采用单一的 LLM 生成路径，不再提供 Python 模板分析与 LLM 分析两套正式模式。

## 9. DeepSeek 报告结构与写作要求

### 9.1 财务报表摘要

| 科目 | 2024年 | 2025年 | 变化金额 | 同比变化率 | 是否重点 |
| --- | ---: | ---: | ---: | ---: | --- |
| 应收账款（万元） | 1,000 | 1,200 | +200 | +20.00% | 是 |

### 9.2 重点科目分析

DeepSeek 应逐项形成完整自然语言段落，而不是只返回 `metric_id`、`fact_id` 或风险标签。每段至少包含上期/本期金额、变化额与比例、已披露原因或明确标记的推断、跨指标合理性判断、授信关注及尽调问题，并引用支持它的 Fact/Metric/Source ID。Python 可以校验这些引用，但不能把 ID 重新渲染成预设分析模板。

### 9.3 专项结论

至少覆盖：盈利与收入质量、营运资金占用、短期偿债与现金流、重大财务异常、公开信息局限。不得在证据不足时笼统写“总体风险可控”或“授信条件良好”。

### 9.4 尽调问题示例

- **货币资金**：是否可以提供主要存款银行及期末余额、受限存款明细？
- **应收账款**：能否提供前五大欠款方、账期/账龄、逾期余额和期后回款？
- **预付款项**：大额预付款是否对应具体合同、锁价安排或供应商优惠？履约进展如何？
- **短期借款**：主要借款银行、余额、到期安排、抵质押及实际用途分别是什么？
- **应付账款**：主要供应商、采购背景、账期及是否存在逾期付款？
- **流水核查（未来授权版本）**：能否提供指定期间银行流水并核实前五大销售回款/采购付款交易对手，区分经营收付与其他往来？

## 10. 异常处理与安全要求

- `missing_source`：数据无有效来源，禁止写成真实值；
- `reporting_scope_conflict`：合并与母公司口径混用，暂停该项同比；
- `unit_or_currency_conflict`：未能换算、或存在汇率口径差异，禁止直接比较；
- `zero_or_small_base`：低/零基期导致变化率误导，使用金额和文字变化描述；
- `restated_or_reclassified`：重述/重分类，须以可比调整后的口径计算，保留对比说明；
- `conflicting_disclosures`：年报及更正公告或不同期信息冲突时，优先权威更正，未解决则标记冲突；
- `bank_details_not_public`：未披露存放银行、贷款银行、交易对手或流水，列入待核查，不虚构；
- `unverified_causal_claim`：原因无直接资料支持时只做标明待核实的推断；
- `invalid_llm_section`：模型段落含不匹配的金额、期间、来源或无支持的事实陈述时，仅拒绝该段并标记“本节未完成”；其他已通过段落和确定性数据产物继续保留；
- `llm_generation_failed`：模型调用或整体输出失败时，保留事实、指标、图表、数据附录和来源，正式分析报告标记未完成，不得生成 Python 模板文字冒充模型研究成果；
- `private_data`：不得抓取或存储未获授权的客户敏感资料；若未来支持上传，应单独完善脱敏、权限、加密和留存规则。

## 11. 第一版验收标准与测试用例

1. 对以岭药业公开年报中的**合并报表**，能在真实来源上完成至少两期的关键科目提取、单位校验和同比计算；所有结果可追溯。
2. 模拟数据 1,000→1,200 的变化率为 **+20.00%**，`requires_deep_analysis=true`；1,000→1,199 时不因同比阈值触发，但重大金额例外仍可触发。
3. 模拟数据 0→100、100→0、负利润由 -100→-200、由正转负、单位冲突、缺失期初值等均有合理处理，不产生 `inf` 或虚假的正增长描述。
4. 报告必须先列金额和变化，再分析原因与合理性；有披露原因引用原始资料，无直接证据则标明假设。
5. 货币资金、应收账款、预付款项、固定资产、短期借款、应付账款、主营业务收入及经营现金流均进入检查清单；获取不到的字段要出具缺失提示。
6. 能识别“应收增长快于收入”“现金流与利润背离”“短债上升但可用现金未知”等至少三种基础信号；这些信号不是自动的违约判断。
7. **第一版银行流水模块处于关闭状态**，不得声称获取到某银行存款银行名单、前五大实际回款客户或采购流水；只在待补清单中提示。
8. 重要数值、已证实原因和事实性结论都有来源 ID；报告中每个重点变化可以回溯到原始披露和确定性的 Python 计算结果。
9. 对真实资料执行的测试与对模拟数据执行的测试必须分开记录；测试失败时明确披露，不为通过验收而填补未知数据。
10. Mock 测试必须证明合格的 DeepSeek/脚本模型段落未经 Python 改写直接进入报告；单段不合格时只标记该节未完成，不能回退到固定分析模板。
11. 正式财务报告必须有实际 DeepSeek 生成正文；Mock 只验证流程与约束，不等同于正式报告或 Live 验收。

## 12. Codex 开发及集成建议

建议存放位置：`.agents/skills/financial-analysis/SKILL.md`。

建议将通用计算工具放在 `credit_research_agent/tools/`，只维护一份业务计算逻辑，避免把公式分别复制在 Skill 脚本和 Agent Tool 中。

建议按如下里程碑开发：

1. **计算内核**：建立科目与来源数据模型，完成同比/财务比率计算和单元测试。
2. **Skill 规范与附注查找**：主 Agent 识别任务后按需加载本 Skill，触发重点科目附注检索。
3. **财务分析文本**：由 DeepSeek 基于结构化上下文撰写，分别表达“事实、已披露原因、推断、待核实问题”并明确引用；Python只做逐段校验和机械组装。
4. **端到端测试**：使用经过人工核查的以岭药业真实年报资料和独立的模拟边界案例，验证模型原文保留、部分章节失败和无模板回退。
5. **未来扩展**：客户合法授权上传详细科目、往来款和银行流水之后，再开发前五大交易对手、银行账户匹配和流水交叉核查模块。

**完成标准**不是“生成几千字报告”，而是“关键数据提取正确、计算准确、DeepSeek 实际完成有证据的分析写作、重要变动有可追溯解释、缺失资料有明确提示”，并且 Python 从未用固定模板替换模型正文。
